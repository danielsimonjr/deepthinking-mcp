# Test Coverage

This document maps the deepthinking-mcp test suite to the code it covers. Use it to
answer one question: is this area tested, and where.

## 1. Overview

The suite uses **Vitest** with the **V8** coverage provider (`vitest.config.ts`). Coverage
excludes `node_modules/`, `dist/`, `*.d.ts`, config files, and the `tests/` tree itself.
`vitest.config.ts` does not set a coverage `thresholds` block, so no minimum percentage
gates the build — coverage reports are informational, not enforced.

Tests mirror the `src/` layout one level down: `tests/unit/<area>/` and
`tests/integration/<area>/` follow the same folder names as `src/<area>/`. A file under
`src/modes/handlers/BayesianHandler.ts` has its unit test at
`tests/unit/modes/handlers/BayesianHandler.test.ts`.

### Layout

| Directory | Files | Purpose |
|---|---|---|
| `tests/unit/` | 101 | One test file per source module — type guards, handlers, validators, exporters, session storage. |
| `tests/integration/` | 72 | Cross-module paths — full tool calls through `src/index.ts`, export round-trips, multi-mode analysis, session lifecycles. |
| `tests/edge-cases/` | 6 | Boundary conditions, malformed input, regressions pinned from past bugs. |
| `tests/performance/` | 4 | Latency, throughput, memory, and stress benchmarks. |
| `tests/utils/` | 5 | Shared fixtures, factories, and assertion helpers used across the other four trees. |
| `tests/test-results/` | — | Reporter output only (HTML/JSON per test file, `TEST_RESULTS_v*.md` summaries). Not test code. |

Total: **183 test files, 5,116 tests**, measured by a full `npx vitest run` on 2026-08-05.
This document does not re-run that measurement; it maps files, not live pass/fail state.

### Running each tier

```bash
npx vitest run tests/unit               # unit only
npx vitest run tests/integration        # integration only
npx vitest run tests/edge-cases         # edge cases only
npx vitest run tests/performance        # benchmarks only
npx vitest run                          # everything
```

`npm run test:publish` sets `SKIP_BENCHMARKS=1`, which excludes `tests/performance/` via the
`exclude` list in `vitest.config.ts` (`**/benchmarks/**` — matched against the performance
directory's benchmark-style file names, not a literal folder rename). Use this script before a
release so a slow machine cannot fail the benchmark thresholds and block a publish.

### Where reports land

`vitest.config.ts` registers two reporters: the built-in `default` console reporter and a
custom `./tests/test-results/per-file-reporter.js`. The custom reporter writes one HTML and
one JSON file per test file into `tests/test-results/html/` and `tests/test-results/json/`,
named `<test-file>-<date>-<PASS|FAIL>.{html,json}`, plus a rolled-up summary under
`tests/test-results/summary/`. Coverage output (`text`, `json`, `json-summary`, `html`
reporters) goes to `./coverage/`, generated by `npm run test:coverage` or any `--coverage` run.

## 2. Coverage by area

Counts are from direct directory listings of `src/` and `tests/unit/`, not estimates.
"Dedicated unit tests" means a `tests/unit/` file whose name and location correspond directly
to a `src/` module. Areas with high src-file counts but low dedicated-unit counts are not
necessarily undertested — several (notably `tools/` and `validation/`) are covered end-to-end
by integration tests instead of per-file unit tests; that trade-off is called out per row.

| Area | `src/` files | Dedicated unit tests | Also exercised by |
|---|---|---|---|
| `types/` | 36 | 10 | Every handler and validator test imports type guards from here. |
| `modes/` (handlers + combinations + causal graph + stochastic) | 50 | 47 | `tests/integration/handlers/`, `tests/integration/mode-handler-delegation.test.ts`. |
| `services/` (ThoughtFactory, ExportService) | 2 | 0 | 63 unit/integration/edge-case/performance files import these two classes directly (no isolated unit test file, but the heaviest-used pair in the suite). |
| `session/` | 4 | 4 | `tests/integration/session-workflow.test.ts`, `multi-session.test.ts`, `edge-cases/session-edges.test.ts`, and 4 `tests/integration/tools/session-*.test.ts` files. |
| `validation/` | 45 | 10 | `tests/integration/validators/mode-validators.test.ts` plus every integration tool test, which sends valid/invalid payloads through the same validators. Only 10 of 35 mode validators have a dedicated unit test — see Gaps. |
| `export/` | 45 | 10 | 12 integration files under `tests/integration/export/` and `tests/integration/exports/`. |
| `proof/` | 13 | 9 | `tests/integration/proof/decomposition.test.ts`. Not imported by `src/index.ts` — see Gaps. |
| `taxonomy/` | 5 | 1 | None beyond the one unit test. Not imported by `src/index.ts` — see Gaps. |
| `cache/` | 3 | 0 | No dedicated test file. Reached only transitively through `session/manager.ts` and `validation/validator.ts`, which each hold their own cache consumer — see Gaps. |
| `utils/` + `interfaces/` | 7 | 4 | `type-guards.ts`, `logger-types.ts`, and `interfaces/ILogger.ts` have no dedicated test; they are exercised as import surfaces by everything else. |
| `tools/` | 18 | 3 | 39 files under `tests/integration/tools/`, one per MCP tool/mode combination — the primary coverage mechanism for this area. |
| `config/` | 1 | 1 | Full 1:1 coverage. |

**Headline:** `modes/` (handlers, combinations, causal graph, stochastic) is the best-covered
area at 47 dedicated unit tests against 50 source files — effectively one test file per
handler. `tools/` and `validation/` look thin by dedicated-unit-test count alone but carry
their real weight in `tests/integration/tools/` (39 files), which drives every schema and
validator through a live tool call. `cache/`, `services/`, and most of `taxonomy/` and
`proof/` are the areas with the least direct, file-level test evidence.

## 3. Unit tests

101 files under `tests/unit/`, organized by the `src/` area they cover.

**`types/` (10 files).** `types.test.ts` covers the core type guards in `src/types/core.ts`.
Nine more files pair a single reasoning mode's type guard with `ThoughtValidator` from
`src/validation/validator.ts`: `abductive.test.ts`, `analogical.test.ts`, `bayesian.test.ts`,
`causal.test.ts`, `counterfactual.test.ts`, `evidential.test.ts`, `gametheory.test.ts`,
`temporal.test.ts`. `recommendations.test.ts` covers `ModeRecommender` in
`src/types/modes/recommendations.ts`.

**`modes/` (47 files).** The largest concentration in the suite:
- `tests/unit/modes/handlers/` (38 files) — one test per file in `src/modes/handlers/`
  (`AbductiveHandler.test.ts` through `TemporalHandler.test.ts`), plus `registry.test.ts` for
  the `ModeHandlerRegistry` singleton in `src/modes/registry.ts`. Every one of the 37 handlers
  listed in the project's handler table has a matching test file — the only area in the
  codebase with complete 1:1 file coverage.
- `tests/unit/modes/combinations/` (3 files) — `conflict-resolver.test.ts`, `merger.test.ts`,
  `presets.test.ts`, covering mode-combination logic in `src/modes/combinations/`.
- `tests/unit/modes/causal/graph/` (3 files) — `centrality.test.ts`, `d-separation.test.ts`,
  `intervention.test.ts`, covering the causal-graph algorithms in
  `src/modes/causal/graph/algorithms/`.
- `tests/unit/modes/stochastic/` (3 files) — `distribution.test.ts`, `rng.test.ts`,
  `statistics.test.ts`, covering `src/modes/stochastic/{models,sampling,analysis}/`.

**`validation/` (10 files).** `tests/unit/validation/validators/modes/` holds one test file
per mode validator for 10 of the 35 modes in `src/validation/validators/modes/`:
`computability`, `constraint`, `cryptanalytic`, `deductive`, `inductive`, `metareasoning`,
`modal`, `optimization`, `recursive`, `stochastic`. The other 25 mode validators have no
dedicated unit test — see Gaps.

**`export/` (10 files).** `file-exporter.test.ts`, `latex.test.ts`, `latex-export.test.ts`,
`profiles.test.ts`, and `proof-decomposition-visual.test.ts` cover the top-level export
modules. `visual/modes/snapshot-baseline.test.ts` pins visual-exporter output against
snapshots. `visual/utils/{document-builders,graph-builders,visual-builders}.test.ts` cover the
fluent builder classes in `src/export/visual/utils/`. `visual.test.ts` (at the `tests/unit/`
root) exercises `VisualExporter` end-to-end across causal, temporal, game-theory, and
Bayesian thought types.

**`proof/` (9 files).** One test file per proof module for 9 of the 13 files in `src/proof/`:
`branch-analyzer`, `circular-detector`, `dependency-graph`, `hierarchical-proof`,
`inconsistency-detector`, `strategy-recommender`, `types` (covers `branch-types.ts`),
`verifier`, `warning-patterns` (covers `patterns/warnings.ts`). `assumption-tracker.ts`,
`decomposer.ts`, `gap-analyzer.ts`, and `index.ts` have no dedicated unit test; they are
reached only through `tests/integration/proof/decomposition.test.ts` — see Gaps.

**`taxonomy/` (1 file).** `taxonomy-system.test.ts` is the only test touching
`src/taxonomy/`, exercising the classifier, multi-modal analyzer, navigator, reasoning-types
catalogue, and suggestion engine together in one file.

**`tools/schemas/` (3 files).** `bounds.test.ts`, `schema-validation.test.ts`, and
`tool-definitions.test.ts` cover input-size limits, Zod schema shape, and the 13 tool
definitions in `src/tools/definitions.ts` and `src/tools/schemas/`.

**`session/` (4 files).** `session-manager.test.ts` and `session-manager-remediation.test.ts`
cover `src/session/manager.ts`. `file-store.test.ts` and `file-store-storage-error.test.ts`
cover `src/session/storage/file-store.ts`, including the error paths a healthy run never hits.

**`utils/` (4 files).** `errors.test.ts`, `logger.test.ts`, and `sanitization.test.ts` cover
`src/utils/{errors,logger,sanitization}.ts`. `file-lock.test.ts` covers
`src/utils/file-lock.ts`, the cross-process lock used by multi-instance session storage.

**`config/` (1 file).** `config-index.test.ts` covers all 15 environment variables read in
`src/config/index.ts`, including the ones marked "not enforced" in the project's own
environment-variable table.

**`benchmarks/` (2 files, not area-specific).** `tests/unit/benchmarks/metrics-performance.test.ts`
and `validation-performance.test.ts` are micro-benchmarks that run as part of the normal unit
suite — distinct from the four benchmark files in `tests/performance/`, which
`SKIP_BENCHMARKS=1` excludes. These two are not skipped by that flag.

## 4. Integration tests

72 files under `tests/integration/`, exercising cross-module paths that a unit test cannot
reach — a full MCP tool call from request to response, an export round-trip, or a session
living across multiple tool invocations.

**`tools/` (39 files) — tool dispatch, one file per tool/mode combination.** This is the
primary way the 13 MCP tools and their 35 validator/schema pairs get exercised end-to-end:
`core-{abductive,deductive,inductive}.test.ts`, `standard-{sequential,shannon,hybrid,
runtime-only}.test.ts`, `mathematics-{core,analysis}.test.ts`, `temporal-{events,relations,
timeline}.test.ts`, `probabilistic-{bayesian,evidential}.test.ts`, `causal.test.ts`,
`counterfactual.test.ts`, `strategic-{gametheory,optimization}.test.ts`,
`analytical-{analogical,cryptanalytic,firstprinciples,metareasoning}.test.ts`,
`scientific-{formallogic,method,systemsthinking}.test.ts`, `engineering.test.ts`,
`algorithmic.test.ts`, `academic-{analysis,argumentation,critique,synthesis}.test.ts`,
`physics.test.ts`, `computability.test.ts`, `analyze.test.ts` (multi-mode analysis),
`common-parameters.test.ts` (parameters shared across all tools), and six
`session-{actions,export-all,lifecycle,multiinstance}.test.ts`-style files covering session
management through the `deepthinking_session` tool.

**`handlers/` (7 files) — handler behavior through the full request path**, distinct from the
unit-level handler tests: `bayesian.handler.test.ts`, `causal.handler.test.ts`,
`counterfactual.handler.test.ts`, `critique.handler.test.ts`, `gametheory.handler.test.ts`,
`synthesis.handler.test.ts`, `systemsthinking.handler.test.ts`.

**`exports/` + `export/` (12 files) — format round-trips.** `exports/{ascii,dot,html,json,
jupyter,latex,markdown,mermaid}.test.ts` each drive a thought through the real export
pipeline and check the rendered output. `exports/mode-specific.test.ts` checks
mode-specific export branches. `export/batch-export.test.ts` covers exporting many sessions
at once. `export/visual/{builders-integration,mode-exporters-snapshot}.test.ts` cover the
visual builder classes wired together and snapshot-pin per-mode exporter output.

**`scenarios/` (4 files) — realistic multi-step workflows.** `complex-branching.test.ts`
(branch/revision chains), `export-roundtrip.test.ts` (create → export → re-import),
`multi-mode.test.ts` (combining modes in one session), `real-world-workflows.test.ts`
(end-to-end usage patterns modeled on actual tool call sequences).

**Root-level integration files (7).** `mcp-compliance.test.ts` and `mcp-protocol.test.ts`
check the server against the MCP specification directly. `mode-handler-delegation.test.ts`
checks that `ModeHandlerRegistry` routes every mode to the right handler.
`session-workflow.test.ts` and `multi-session.test.ts` cover session lifecycles across
multiple concurrent sessions. `error-handling.test.ts` and `index-handlers.test.ts` cover
`src/index.ts`'s tool-call dispatch and its error responses.

**`modes/` (1 file) and `proof/` (1 file) and `validators/` (1 file).**
`modes/causal-graph.test.ts` covers causal graph construction through the tool layer.
`proof/decomposition.test.ts` is the only test that reaches `assumption-tracker.ts`,
`decomposer.ts`, and `gap-analyzer.ts` — none of which has a dedicated unit test.
`validators/mode-validators.test.ts` imports **the same 10 validators that already have dedicated
unit tests** — it does not offset the others, contrary to what this document previously claimed.
The real cross-cutting coverage is `tests/unit/validation/validator-contract.test.ts`, which
discovers validator files via `import.meta.glob` and asserts the shared contract across all 35, so
a new validator is covered the moment its file exists.

## 5. Edge cases and performance

### Edge cases (6 files, 35 numbered `T-EDG-*` cases + 10 `T-REG-*` regression cases)

Each edge-case file groups a run of sequentially numbered scenarios, which makes an
individual case easy to find by ID:

- **`input-validation.test.ts`** — `T-EDG-001` to `T-EDG-012`: missing required parameters
  (`thought`, `thoughtNumber`, `totalThoughts`, `nextThoughtNeeded`), out-of-range values
  (`thoughtNumber` zero or exceeding total, `totalThoughts` zero, `uncertainty` outside
  `[0,1]`), an invalid mode string, an empty thought string, and `null` parameters.
- **`type-validation.test.ts`** — `T-EDG-013` to `T-EDG-018`: wrong JavaScript type in each
  direction (string where a number is expected, object where an array is expected, and so
  on), plus nested-object type validation.
- **`boundaries.test.ts`** — `T-EDG-019` to `T-EDG-024`: maximum session size, maximum
  thought length, maximum array sizes, maximum nesting depth, and both empty-array and
  empty-object handling — the practical ceiling checks behind the `MCP_MAX_*` config values.
- **`session-edges.test.ts`** — `T-EDG-025` to `T-EDG-030`: resuming a session that does not
  exist, exporting an empty session, deleting an active session, switching mode on a
  completed session, concurrent modification, and session ID collision.
- **`error-responses.test.ts`** — `T-EDG-031` to `T-EDG-035`: error message structure, error
  code consistency, whether error details are included, that stack traces are excluded from
  client-facing errors, and graceful degradation under failure.
- **`regression.test.ts`** — `T-REG-001` to `T-REG-010`: bugs pinned so they cannot silently
  return, covering `undefined` handling in visual exporters, multi-thought visual export,
  the experimental-modes type list, schema alignment between hand-written JSON and Zod,
  optional-property type guards, tool registration completeness, mode-routing accuracy,
  session persistence, export completeness, and consistent error handling across tools.

### Performance (4 files, 20 numbered `T-PRF-*` benchmarks)

- **`latency.test.ts`** — `T-PRF-001` to `T-PRF-005`: single-thought response time,
  10-thought session time, export response time, mode-switch response time, session-resume
  time.
- **`throughput.test.ts`** — `T-PRF-006` to `T-PRF-010`: 100 thoughts/second sustained,
  10 and 50 concurrent sessions, rapid mode switching, bulk export operations.
- **`memory.test.ts`** — `T-PRF-011` to `T-PRF-015`: memory footprint with 100 sessions,
  memory with a single 1000-thought session, memory cleanup after delete, cache
  effectiveness, and memory-leak detection. This file needs a real garbage collector to make
  its heap-delta assertions meaningful — see the `NOTE on GC` comment in `vitest.config.ts`;
  it calls `v8.setFlagsFromString` itself to get one, because worker-thread pools reject an
  `--expose-gc` execArgv.
- **`stress.test.ts`** — `T-PRF-016` to `T-PRF-020`: 10,000 total thoughts, 100 concurrent
  sessions, rapid create/delete cycles, an extended-runtime simulation, and recovery from
  resource exhaustion.

**Benchmark skipping.** `SKIP_BENCHMARKS=1 npx vitest run` (what `npm run test:publish` sets)
excludes everything matching `**/benchmarks/**` in `vitest.config.ts`'s `exclude` list. That
pattern is a directory-name match, not a file-name one — it removes `tests/performance/` from
the run (its four files hold the true benchmarks) while leaving the two
`tests/unit/benchmarks/*.test.ts` micro-benchmark files in place, since the exclude glob is
matched against the discovered test file's own path segments and the unit ones sit under a
literal `benchmarks/` directory too — check the current exclude list in `vitest.config.ts`
before assuming either way, since a rename on either side would change which set is caught.

## 6. Test utilities

`tests/utils/` holds shared fixtures so individual test files build scenarios instead of
hand-rolling thought objects. Everything is re-exported from `tests/utils/index.ts`; import
from there rather than reaching into an individual file.

- **`thought-factory.ts`** — the largest helper file. Builders for the three foundational
  reasoning modes: `createInductiveThought` / `createInductiveWithObservations` /
  `...WithPattern` / `...WithGeneralization` / `...WithConfidence` /
  `...WithCounterexamples` / `...WithSampleSize` / `createCompleteInductiveThought`; the
  matching `createDeductive*` family including `createClassicSyllogism`; the matching
  `createAbductive*` family including `createCompleteAbductiveThought`. Structural helpers
  for branching (`createThoughtWithBranch`, `createRevisionThought`,
  `createThoughtWithDependencies`) and multi-step sequences (`createInductiveSequence`,
  `createDeductiveProofChain`, `createAbductiveRefinementSequence`).
- **`session-factory.ts`** — `createTestSessionManager()` returns a ready `SessionManager`
  for tests that need one without touching real session storage; `generateTestSessionId()`
  produces unique session IDs to avoid collisions between test files run in parallel.
- **`assertion-helpers.ts`** — domain-specific assertions layered on top of `expect()`:
  mode/shape checks (`assertThoughtMode`, `assertValidBaseThought`, `assertIsRevision`,
  `assertIsBranch`), per-mode structural checks for inductive/deductive/abductive thoughts
  (`assertHasObservations`, `assertHasPremises`, `assertHasHypotheses`,
  `assertHypothesesHaveScores`, and their siblings), session checks (`assertValidSession`,
  `assertSessionHasThoughts`, `assertSessionMode`), validation-result checks
  (`assertValidationPassed`, `assertValidationFailed`, `assertHasErrorCode`,
  `assertHasWarning`), and general-purpose numeric/collection checks
  (`assertValidProbability`, `assertUniqueItems`, `assertInRange`).
- **`mock-data.ts`** — static fixture data consumed by the factories above:
  `SAMPLE_OBSERVATIONS`, `SAMPLE_PATTERNS`, `SAMPLE_GENERALIZATIONS`,
  `SAMPLE_COUNTEREXAMPLES`, `CONFIDENCE_LEVELS`, `SAMPLE_SIZES`, `CLASSIC_SYLLOGISMS`,
  `LOGIC_FORMS`, `SAMPLE_PREMISES`, `SAMPLE_CONCLUSIONS`, `SAMPLE_HYPOTHESES`,
  `ABDUCTIVE_OBSERVATIONS`, `BEST_EXPLANATIONS`, `SAMPLE_ASSUMPTIONS`,
  `SAMPLE_DEPENDENCIES`, `BRANCH_DATA`, `REVISION_DATA`, `UNCERTAINTY_LEVELS`, and three
  larger fixture blocks for multi-step sequences (`INDUCTIVE_SEQUENCE_DATA`,
  `DEDUCTIVE_PROOF_CHAIN_DATA`, `ABDUCTIVE_REFINEMENT_DATA`).

A contributor adding a test for inductive, deductive, or abductive reasoning should start
here rather than constructing thought objects by hand — the factories already produce
schema-valid input, and the assertion helpers already know each mode's required fields.

## 7. Gaps and risks

These are the areas with the least direct test evidence, named by file so they are easy to
act on.

- **`src/proof/` is not reached from `src/index.ts`.** Grepping `src/index.ts` for `proof`
  and `taxonomy` finds only comments — no import wires the proof-decomposition engine
  (`decomposer.ts`, `gap-analyzer.ts`, `assumption-tracker.ts`, `inconsistency-detector.ts`,
  and the rest) into a live MCP tool call. Its 9 unit tests plus
  `tests/integration/proof/decomposition.test.ts` are the only thing exercising this module;
  they test the code in isolation, not through the server a client actually talks to.
- **`src/taxonomy/` is not reached from `src/index.ts` either**, and more completely than
  `proof/`: none of its five files (`classifier.ts`, `multi-modal-analyzer.ts`,
  `navigator.ts`, `reasoning-types.ts`, `suggestion-engine.ts`) is imported anywhere in `src/`
  outside the `taxonomy/` directory itself. `navigator.ts` and `suggestion-engine.ts` are not
  even imported by their own sibling files. The single `taxonomy-system.test.ts` unit test is
  the entire test surface for this module, and — like `proof/` — it tests code that a running
  server never calls.
- **25 of 35 mode validators in `src/validation/validators/modes/` have no dedicated unit
  test.** Only `computability`, `constraint`, `cryptanalytic`, `deductive`, `inductive`,
  `metareasoning`, `modal`, `optimization`, `recursive`, and `stochastic` do. The other 25
  (including `abductive`, `bayesian`, `causal`, `mathematics`, `physics`, `temporal`, and 19
  more) are validated only as a side effect of `tests/integration/tools/*.test.ts` sending
  payloads through the full tool pipeline, or via the one cross-cutting
  `tests/integration/validators/mode-validators.test.ts`. A validator-specific regression
  (an accepted value that should be rejected, or vice versa) in one of the 25 could pass
  every integration test that happens to send only valid input for that mode.
- **`src/cache/` (`index.ts`, `lru.ts`, `types.ts`) has no dedicated test file at all.** It is
  a distinct LRU cache implementation from the one built into
  `src/validation/cache.ts` (which has its own tests via `validation-performance.test.ts`).
  The standalone `src/cache/` module is consumed by `src/session/manager.ts` and
  `src/session/SessionMetricsCalculator.ts`, and is exercised only as a side effect of
  session tests — nothing tests eviction, capacity limits, or TTL behavior in the cache
  module directly.
- **`src/services/ThoughtFactory.ts` and `src/services/ExportService.ts` have no isolated
  unit test file**, despite being the two most-imported classes in the test suite (63 files
  import one or both directly). Coverage is real but comes entirely from integration,
  edge-case, and performance tests driving them through realistic call patterns — there is no
  single file to check first when either class changes.
- **`src/utils/type-guards.ts`, `src/utils/logger-types.ts`, and
  `src/interfaces/ILogger.ts` have no dedicated test.** All three are narrow (type
  predicates and a type-only interface), so the risk is low, but a change to a type guard's
  runtime check would not be caught by a file-level test — only indirectly, by whatever
  handler test happens to exercise the guard.

## 8. Running the suite

```bash
# Everything, once, with coverage
npm run test:run

# Everything, skipping the four benchmark files, with coverage — used before publish
npm run test:publish

# Watch mode (re-runs on file change)
npm test

# Coverage report only, no other reporter changes
npm run test:coverage

# A single file
npx vitest run tests/unit/modes/handlers/BayesianHandler.test.ts

# A directory
npx vitest run tests/unit/proof

# By name pattern (matches describe/it text, not file names)
npx vitest run -t "T-EDG-019"
npx vitest run -t "Bayesian"
```

`npm run test:debug` and `npm run test:all` set `VITEST_REPORT_MODE` to `debug` and `all`
respectively before running with coverage — `debug` surfaces failed-file detail from the
custom per-file reporter, `all` forces it to write output for every file, not only changed
ones. Both still run the full suite; the env var changes reporter verbosity, not which tests
run.

Coverage HTML lands in `./coverage/index.html` after any `--coverage` run; open it directly
rather than reading the JSON summary by hand.
